# Agent Operating Contract (condensed)

Read this + spec.md + PROGRESS.md + Plan.md at the start of every session. Do not re-read the full contents of any file marked DONE in PROGRESS.md unless you're about to edit it or its check fails below.

**PROGRESS.md** (repo root, one line per file):
`- [STATUS] path — purpose — notes: <blank or SUBMISSION_NOTES.md #N>`
STATUS = DONE | WIP | BLOCKED. Two tiers of files:
- **Logic tier** (any file in `src/lib/` that touches numbers, DB writes, encryption, parsing, validation, or data transformation — not just the examples below: money helper, encrypt/decrypt, Data Sanity validators, invoice-confirm transaction, inline total-edit, idempotency check, dashboard math, import/export column mapping + row transforms + **persistence**, transaction CRUD, LLM dispatcher, settings resolver): DONE only if `tsc --noEmit` passes AND a test exists and passes that exercises it with a concrete mock/example number or input, asserting a specific expected value — not that it compiles or runs without throwing. `toBeDefined()`/`not.toThrow()`-only assertions don't count. **`toHaveBeenCalled()`-only assertions don't count either** — a mock being invoked proves nothing about what it was invoked *with*; assert on the actual argument/return value.
  - A helper (e.g. `encrypt`/`decrypt`) is not DONE merely because it exists and passes its own unit test — it is DONE only once something in the real request path actually calls it. A tested-but-uncalled function is a logic-tier file stuck at WIP with a note saying what needs to call it.
- **UI tier** (page/table/form components, filters, status badges, review screen rendering, guardrail screen, settings page UI, column mapping screen UI): DONE if `tsc --noEmit` passes, it renders/behaves per spec, **and every interactive element that implies a write (submit, confirm, delete, save, import, export) has a real handler wired to a real endpoint — not a `disabled` button, an empty `onSubmit`, or a `// TODO: wire this up` comment.** A form that renders correctly but does nothing on submit is not DONE, it's WIP.
- **Data-page tier** (async server components that fetch data before rendering: dashboard page, invoices page, transactions page, settings page): DONE only if it actually queries the database — never an empty array literal (`[]`) or a hardcoded zero (`0`, `{d30:0,d60:0,d90:0}`) standing in for a real query. If the underlying lib file isn't ready yet, the page stays WIP, full stop — it is never committed with placeholder data "to unblock the next file." A mock-number test is not required (values depend on live DB state), but the page must demonstrably call the lib function and pass its real result down.
- **Secrets, everywhere:** a field never sends a decrypted or plaintext secret value (API keys, `APP_ENCRYPTION_KEY`) into a server-component's props/initial render passed to a client component — even into a `type="password"` input's `value`. Client-rendered HTML is visible in the page source regardless of input type. Prefill secret fields with an `isSet: boolean` flag or a fixed masked placeholder, never the real value; only overwrite on the server when the user submits a non-empty new value.
If unsure which tier a file is, default to logic tier — it never touches a number or a DB write only if it's pure display/layout.
No file goes DONE with a TODO/mock/placeholder regardless of tier. If a logic-tier test genuinely can't be written yet (e.g. blocked on a dependency), it stays WIP with a note explaining why, never DONE with an excuse.

**Test integrity (anti-gaming, logic tier only):** the expected value in every assertion must be derived independently from spec.md — a number you could work out by hand from the spec text — never copied from whatever the implementation currently outputs. Forbidden: a test that recomputes the same formula as the implementation and compares the two (both can be wrong identically); an expected value with no visible derivation. Every test file's top comment must state the expected value AND the one-line spec rule it comes from, e.g. `// spec: round once at final sum, not per line-item → 5.6+4.9=10.5 → 10 or 11, never 11 from (6+5)`. This comment is what a human spot-checks — it must be readable without opening the implementation.
**PROGRESS.md format (repo root):**
- Top of file: exactly two lines, overwritten in place each commit — `Current focus:` / `Remaining work:`
- Then one line per file: `- [STATUS] path — purpose — notes: <blank or SUBMISSION_NOTES.md #N>`

**Git — one commit per completed file, immediately on DONE:**
1. Confirm tsc+test passed.
2. Stage only that file (+ its test) — never `git add .`/`-A`. Check `git diff --cached` for stray `.env`/secrets before commit.
3. Message: `"<path>: <one-line purpose>"`.
4. Never `--force`, `--amend` on non-tip commits, `rebase` shared history, or `--no-verify`.
New fixes to an already-committed file = new commit, never rewritten history.
**"One file" is literal, not "one feature."** A commit touching 9 files because they're all part of "the UI pages" is a contract violation, not a convenience — it breaks the resume check's ability to verify any single file's DONE status against git log. If several files are genuinely interdependent (e.g. a page and the table component it renders), that's still N commits, made back-to-back, not one.
**Sequencing:** a data-page tier file that depends on an unfinished lib file is not started yet — work the lib file to DONE first. Never commit a page early "to make progress" with placeholder data; that page is WIP until its dependency is DONE and it's fully wired, and it is logged as WIP in PROGRESS.md, not silently skipped.

**Resume check (new session, not mid-session):** before trusting any DONE entry — run `tsc --noEmit` on it; for logic-tier files, also re-run its mock-number test; for both tiers, confirm a matching commit exists in `git log`. Any required check fails → downgrade to WIP/BLOCKED, fix before continuing. Git log is ground truth over PROGRESS.md's self-attestation.
Also run `git status --porcelain` at the start of every resume check. Any tracked-but-modified or untracked file that the build/test infra actually depends on (config files, the test runner's own config, a `package.json` script someone runs) is a real gap: a fresh clone of this exact commit must be able to run `tsc --noEmit` and the test suite with no extra setup beyond `npm install`. If it can't, commit what's missing before doing anything else.

**SUBMISSION_NOTES.md**: numbered entries, format `N. <file>: <ambiguity> → <how you resolved it>`, e.g. `1. import-export.ts: spec says amounts are "pre-signed" but doesn't state the fallback when a row has no sign, no mapped direction column, and no override → defaulted to expense (isIncome=false), since imported rows are predominantly costs; never silently treat unmarked rows as income.` Every `notes:` pointer in PROGRESS.md resolves to one of these. An empty SUBMISSION_NOTES.md with non-empty `notes:` fields in PROGRESS.md, or a codebase with visible unresolved ambiguities (inconsistent number formatting, an unstated rounding assumption, a field repurposed for something its name doesn't say) and an empty SUBMISSION_NOTES.md, means notes were owed and not written — fix retroactively before the file counts as DONE.

**Plan.md** (Section 5 item level only, never per-file):
`- Item N (name) — status — current step — remaining`

**General:** no `any`/ts-ignore/placeholders/TODOs/dead code. Only add a package when a file actually imports it. Never bump an existing dependency version silently. Lockfile changes commit with the file that introduced the import.
Never pass an empty literal array (`[]`) or a hardcoded zero as a placeholder to a data-displaying component. Either fetch the data or render an explicit loading/"No data" state.
Prefer server components. Only add `"use client"` when the component uses hooks, browser APIs, or event handlers needing interactivity.
If a schema column must be repurposed for something other than its literal name implies (e.g. storing a dedup hash in a field named for something else), that is a code smell to avoid first — check whether an existing, more honestly-named nullable column can carry it instead — and if repurposing is genuinely necessary, it must be commented at the point of use and logged in SUBMISSION_NOTES.md. Never silently overwrite a named field with data that doesn't match its name (e.g. writing a hash into a column called `raw_llm_response`) — the next person reading that column believes its name.
